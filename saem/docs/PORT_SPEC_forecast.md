FIDELITY RULES. (1) Same arithmetic in the same order: accumulate sums left to right exactly as the JS loops do, never reorder, never use std::accumulate with a different order, no fast-math; the build already passes -ffp-contract=off. (2) JS Map/Set iterate in insertion order and a Map.set on an existing key keeps its original position; summation over a Map (dot products, norms, cluster sums) depends on that order, so intern tokens and keep insertion-ordered vectors (core/src/util.hpp has OMap; for speed use token ids with a hash lookup plus an insertion-ordered vector of (id, weight)). (3) Array.prototype.sort is stable: use std::stable_sort with a comparator that reproduces the JS comparator including `||` chains and NaN behaviour. (4) Math.round -> js_round; (5) text handling is on UTF-16 code points: featureTokens lower-cases, strips ' ’ `, matches /[a-zऀ-ॿ]{2,}/g; use the u32 helpers in util.hpp. (6) Numbers inside strings must print with jsnum() (numfmt.hpp). (7) libm: V8's Math.exp/log/pow can differ from glibc in the last ulp; the harness tolerates relative 1e-9, but if an ulp difference flips a discrete decision (a tie in a sort, a threshold) report it to me instead of hacking around it. (8) If you believe the JS has a bug, replicate it anyway and list it in your report.

PERFORMANCE. A 30-year bank of about 1500 questions with K=40 must analyze in a few seconds in -O2. The JS is O(folds x clusters x vector size), so do not use std::map<string,...> in inner loops.
